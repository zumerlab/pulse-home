# Pulse and Home Assistant: integration options

Research of 30/10/2026. It reads the current Home Assistant docs (user docs, contributor docs, release notes and developer blog), checks the main claims against the local Home Assistant in Docker (2026.5.4, frontend 20260429.4) and in Chromium 152, and looks at how other dashboards reached users.

Question: Pulse talks to Home Assistant through its own WebSocket client today. Is that the best way in, or are there others that reach more people?

## Short answer

**Keep the WebSocket, but stop treating "standalone app" as the product.** The WebSocket is the right *transport*: it's what Home Assistant's own frontend and mobile apps use, and every other option ends up on it anyway. What decides reach is the *shell* Pulse ships in, and in 2026 the shell with the most reach is the inside of Home Assistant:

1. **From 2026.11 (stable 4/11/2026), HACS is built into Home Assistant as the Marketplace**, on every install type (Docker included), with install counts and stars on each listing. A Pulse card listed there is one click from every Home Assistant user. Before this, HACS was a separate install that about 71% of reporting installs had.
2. **Home Assistant now lists third-party dashboards in its own "New dashboard" dialog** (custom dashboard strategies, under "Community dashboards", since 2026.5). Pulse can be a dashboard type users pick, not a URL they type. Confirmed in the local frontend bundle.
3. Inside Home Assistant, Pulse gets **for free** what the standalone app has to build: login, users, remote access (Home Assistant Link / Nabu Casa, any reverse proxy), the Companion apps on iOS and Android, kiosk tools, Cast to Nest Hub.

So the recommendation is **one Pulse core, several shells**:

| Shell | Role | Reach |
|---|---|---|
| **Custom card + dashboard strategy**, in the Marketplace | Main channel, free | Every install, every device that shows Home Assistant |
| **Standalone web app** (today's prototype, cleaned up), as Docker image and Home Assistant App | Wall panels, round screens, kiosks; the place for paid features | Anyone who can open a URL; App installs on HA OS (~80%) |
| ESPHome / LVGL export | Later, maybe: a small round knob | Makers |

The work this needs in Pulse is small: the prototype only touches eight members of its Home Assistant client (`states`, `unit`, `status`, `version`, `call`, `onChange`, `onStatus`, `connect`). Implementing those on top of the `hass` object the frontend hands to cards is about fifty lines. The model (`model.ts`) doesn't change.

One business constraint changes the plan in `../coordinacion/pulse-venta-ha.md`: **the Marketplace catalog requires an OSI license that doesn't restrict use.** FSL (the license suggested for Pulse) isn't one. The Marketplace build has to be MIT (or similar), and paid features have to live outside it: in the standalone app, in a "Pulse Pro" key, or in hardware bundles. See [Business](#business-implications).

## 3. The options in detail

### A. Standalone web app (what exists)

**How it works today.** `server/homeassistant.ts` logs into Home Assistant with user and password (or a long-lived token), keeps the refresh token in memory and hands the browser a short access token. Vite proxies the WebSocket so the browser talks to its own origin. One socket does `get_states`, `subscribe_events` (`state_changed`) and `call_service`.

**What's good about it.**
- Full control of the screen: no header, no sidebar, no grid. This matters for round screens (720–1080 px) and wall panels.
- Works with any Home Assistant install and doesn't depend on frontend internals.
- It's where a paid product can live: its own license, its own distribution.
- The WebSocket API is the API Home Assistant's own frontend and mobile apps use "for nearly everything" ([WebSocket API](https://contributors.home-assistant.io/core/internals/websocket-api/)). Commands provided by integrations are described as "a contract" because the apps depend on them. There is no formal stability policy, but core commands are safe in practice.

**What costs.**
- **Login.** The current server-side login with a stored password is fine for a demo, not for users. The official way is the OAuth flow Home Assistant implements in IndieAuth style: `client_id` is Pulse's own URL, no registration, PKCE S256 supported, access tokens last about 30 minutes, refresh tokens expire after 90 days unused ([auth API](https://contributors.home-assistant.io/core/internals/auth-api/)). The official library [`home-assistant-js-websocket`](https://github.com/home-assistant/home-assistant-js-websocket) (Apache-2.0, 9.8.1 on 29/10/2026, no dependencies) does it with `getAuth()` and also gives `subscribeEntities`, `callService` and reconnection. With it, the Node server isn't needed for auth.
- **Remote access.** A Pulse served over HTTPS can't open `ws://` to a LAN Home Assistant (mixed content). It has to go through the same URL the user uses remotely (Home Assistant Link, a reverse proxy, Tailscale).
- **Users install a second thing** and keep it updated. ha-fusion, the most popular standalone dashboard (3.0k stars), is "no longer actively maintained" since 2024; a fork carries it.

**Verified locally:**
- The WebSocket accepts any `Origin`: a connection with `Origin: https://example.org` got `auth_required`. So a Pulse on another origin can use the WebSocket directly.
- REST refuses other origins: a CORS preflight from `https://example.org` got 403. The only default allowed origin is `https://cast.home-assistant.io` (`DEFAULT_CORS` in core). Pulse would need the user to add its origin in HTTP settings if it uses REST, or stay on WebSocket only. Camera images work through `entity_picture`, which already carries a token.
- Listing areas, devices, entities and floors (`config/*_registry/list`) doesn't require admin; only changes do. A non-admin user can run Pulse.

**Improvements worth taking even if A stays primary:**
- Use `subscribe_entities` instead of `subscribe_events` + `get_states`. It sends initial states and compressed diffs in one subscription; the Android app measured 35–90% less traffic when it switched ([PR](https://github.com/home-assistant/android/pull/2942)).
- Read areas and devices from the registries to build systems per home, not from a list of demo entity ids.

### B. Home Assistant App (ex add-on) with ingress

Option A packaged as a container the Supervisor runs. This is how GlassHome and ha-fusion reach users.

- **Manifest** `config.yaml`: `name`, `version`, `slug`, `description`, `arch` (`aarch64`, `amd64`), and for the sidebar `ingress: true`, `ingress_port`, `panel_icon`, `panel_title`, `panel_admin` (default `true`: **set it to `false`** or only admins see Pulse) ([configuration](https://contributors.home-assistant.io/apps/reference/configuration/)). The local core confirms `require_admin=data.admin` for app panels.
- **Ingress** serves the app under `/api/hassio_ingress/<token>/`. Home Assistant handles the login ("Do not ask for a login"). The user arrives in `X-Remote-User-Id`, `X-Remote-User-Name` and `X-Remote-User-Display-Name`, trusted only from `172.30.32.2`. WebSockets work. **Relative URLs only**: Vite needs `base: './'` ([ingress](https://contributors.home-assistant.io/apps/guides/ingress/)).
- **Talking to Core**: `ws://supervisor/core/websocket` with `SUPERVISOR_TOKEN`. Through this proxy the app **acts as admin**, whoever is looking ([communication](https://contributors.home-assistant.io/apps/guides/communication/)). Per-user permissions are lost unless Pulse also does the OAuth flow per user.
- **Distribution**: any GitHub repo with `repository.yaml`. Users add it with a My link (`https://my.home-assistant.io/redirect/supervisor_add_addon_repository/?repository_url=…`). No review, no store. Images on GHCR, multi-arch, built with the official builder actions ([publishing](https://contributors.home-assistant.io/apps/guides/publishing/)).
- **Reach**: HA OS only (~80% of reporting installs). Container users (~18%) need the Docker image of A.

Verdict: good as the packaging of A, not as the main channel. It shows Pulse inside Home Assistant's sidebar but still in an iframe-like page, and gives up per-user identity unless more work is done.

### C. Custom card

The way most of the community's UI reaches users (Mushroom 5.2k stars, Bubble Card, button-card).

**Contract** ([custom card](https://contributors.home-assistant.io/frontend/custom-ui/card/)):
- Standard custom element. `setConfig(config)` (required; throw to show an error card), `set hass(hass)` on every state change, `getCardSize()` for masonry, `getGridOptions()` for sections (12 columns, 56 px rows; `columns: "full"`, `rows: "auto"`).
- Registered with `customElements.define('zumer-pulse', …)` and `window.customCards.push({type, name, description, preview, documentationURL, getEntitySuggestion})`.
- Visual editor: `static getConfigForm()` returns a schema with the same selectors blueprints use (`entity`, `area`, `select`…). No need to write an editor element.
- Calls: `hass.callService`, `hass.callWS`, `hass.connection.subscribeMessage` (the connection is a `home-assistant-js-websocket` instance). `hass` also carries `areas`, `devices`, `entities`, `floors`, `config` (unit system), `user`, `themes`, `locale`.
- Any library or none; Lit isn't required. Internal `ha-*` elements are unsupported and change often. `ha-card` is the practical exception.

**Full screen.** Put the card in a **panel view** (`type: panel`): one card, full width, full height (`card.layout = "panel"`, host at 100%), no border or shadow ([panel view](https://www.home-assistant.io/dashboards/panel/)). This is the natural home for the radial object. In sections, the card takes `columns: "full"`; a "small Pulse" (one system) fits a 6×6 cell.

**Performance.** `hass` is a new object on every change in the house. Compare `hass.states[id]` by reference and repaint only the systems whose entities changed. Or request only the `states` context with a `context-request` event (documented in the card page). Pulse already repaints by changed entities, so this maps directly.

**Shadow DOM: two things to solve, both verified.**
1. **Styles.** A `css` resource goes into `document.head`, and cards live deep inside Home Assistant's shadow roots, so a page-level stylesheet can't reach card content. Orbit's and Zumly's CSS have to ship inside the card (a `<style>` in its shadow root, or `adoptedStyleSheets`).
2. **`@property` inside a shadow root is ignored.** Tested in Chromium 152: a rule declared in a shadow-root stylesheet doesn't register (`getComputedStyle` gives nothing); the same rule in `document.head` works inside the shadow root. Orbit declares five (`--o-dir-x`, `--o-dir-y`, `--o-value-angle`, `--o-ellipse-x`, `--o-ellipse-y`). The card has to register them once at document level. This is an Orbit task (export them apart, or register them from JS). Noted in `PENDIENTES.md` under Orbit.

**Zumly in a card.** `new Zumly({ mount })` accepts an element, so it can mount inside a shadow root. Its "click outside to close" listener is on `document`; events from inside a shadow root arrive retargeted to the host, so the menu could close on any click inside the card. To test. Inside a card, Zumly's hash router should stay off (the dashboard owns the URL).

**Theme.** Use Home Assistant's semantic tokens (`--ha-color-*`, `--ha-space-*`, `--ha-font-*`, plus legacy `--primary-color`, `--card-background-color`) so dark mode and user themes work ([theming](https://contributors.home-assistant.io/frontend/architecture/theming/)). Pulse's urgency colours can stay its own, but backgrounds and text should follow the theme.

**Where it shows up for free:** desktop browsers, the iOS and Android Companion apps (they render the same frontend in a WebView; this is architecture, not stated in the docs), wall tablets with Fully Kiosk or kiosk-mode, Nest Hub via Cast (`cast.show_lovelace_view`, needs HTTPS; custom cards on Cast have a mixed history).

### D. Dashboard strategy: "Pulse" as a dashboard type

A strategy is code that writes dashboard config when the dashboard loads ([strategies](https://contributors.home-assistant.io/frontend/custom-ui/strategy/)). Home Assistant builds its own dashboards this way: `home`, `areas`, `energy`, `map`, `original-states` are built-in strategies.

- Element `ll-strategy-dashboard-zumer-pulse` with `static async generate(config, hass)`. Config: `strategy: { type: custom:zumer-pulse, … }`.
- Registered with `window.customStrategies.push({ type: 'zumer-pulse', strategyType: 'dashboard', name: 'Pulse', description, documentationURL })`. The **New dashboard dialog lists it under "Community dashboards"**. Confirmed in the local bundle: the dialog reads `window.customStrategies` filtered by `strategyType === 'dashboard'`.
- Regenerates on registry changes (entities, devices, areas, floors), not on state changes. `registryDependencies` and `shouldRegenerate` tune this.
- Users can "Take control" and get the generated YAML to edit.

For Pulse: `generate()` reads areas, devices and entity domains, groups them into systems (Lights, Climate, Security…, the same seven as the prototype) and emits one panel view with a `custom:zumer-pulse`, plus maybe one view per system. This replaces the hard-coded demo entities with "your house, whatever it has", which the README already wants ("another installation builds its own object").

Same JavaScript file as the card. Cost: small once C exists.

### E. Section strategy (2026.11)

Same idea for one section inside a sections view: "Automatic section" → "Community sections". A one-system Pulse (just Climate, just Security) inside someone's existing dashboard. Lowers the commitment: users don't have to switch dashboards to try Pulse.

### F. Custom panel

A full page in the sidebar outside the dashboard system ([custom panel](https://contributors.home-assistant.io/frontend/custom-ui/panel/)).

- Element receives `hass`, `narrow`, `route`, `panel`. It owns the whole page, including the header and the sidebar toggle on phones.
- Only two ways to add one: `panel_custom:` in `configuration.yaml` plus restart, or `panel_custom.async_register_panel()` from a **custom integration**. No UI.
- The integration route is how a Marketplace "Integration" could ship a Pulse page: register the panel, serve the bundle with `hass.http.async_register_static_paths`, optionally expose WebSocket commands (`websocket_api.async_register_command`) for Pulse-specific state such as silenced alerts, per user (`connection.user`).

Verdict: worth it only if Pulse needs **server-side state inside Home Assistant** (shared silences, rules that run when no screen is open, notifications). For the UI alone, C + D in a panel view gives the same full screen without Python.

### G. Custom view layout

Documented: an element used as `type: custom:pulse-view` receives the view's `cards` as ready elements and places them itself ([custom view](https://contributors.home-assistant.io/frontend/custom-ui/view/)). A "Pulse view" could put any Home Assistant card on orbits by urgency. An interesting Orbit showcase, but it's not Pulse (Pulse draws its own channels). Experiment, not product.

### H. Webpage dashboard / card (iframe)

Home Assistant shows a URL in an iframe (replaces the old `panel_iframe`). Zero integration, but:
- No `hass`: the page logs in by itself.
- HTTPS Home Assistant can't embed an HTTP Pulse (the card shows an error).
- Home Assistant sends `X-Frame-Options: SAMEORIGIN`, so the reverse (Pulse embedding Home Assistant) is off by default.

Use it as glue to put a standalone Pulse in the sidebar, not as a channel.

### I. Card features and badges

Tile card features (42 px high), area and thermostat card features, and badges are documented extension points ([card feature](https://contributors.home-assistant.io/frontend/custom-ui/card-feature/), [badge](https://contributors.home-assistant.io/frontend/custom-ui/badge/)). Too small for the object. A "Pulse ring" badge (one dot per system, coloured by urgency) could be a cheap teaser that links to the Pulse dashboard.

### J. ESPHome / LVGL round screens

ESPHome's LVGL component has `arc`, `meter` (scales, needles, ticks), `canvas` and pages; round panels from 1.28" (240×240) to 466×466 AMOLEDs are supported ([LVGL](https://esphome.io/components/lvgl/), [widgets](https://esphome.io/components/lvgl/widgets/)). Each entity is declared in YAML at compile time and bound with `homeassistant` sensors. Pulse's HTML can't run there, but its model could **generate the YAML**: rings by urgency, one page per system. Matches the "satellite knob" idea in `pulse-pantallas-redondas.md`. Later.

### Closed surfaces

Android and iOS widgets, Wear OS tiles, Apple Watch complications, CarPlay, Android Auto: all built into the Companion apps and configured by the user; none accepts third-party UI ([Android widgets](https://companion.home-assistant.io/docs/integrations/android-widgets), [iOS widgets](https://companion.home-assistant.io/docs/integrations/ios-widgets), [Wear OS](https://companion.home-assistant.io/docs/wear-os), [Apple Watch](https://companion.home-assistant.io/docs/apple-watch)). Pulse reaches them only through data: e.g. a template sensor "Pulse: 2 alerts" that a watch ring shows, or actionable notifications sent by automations.

## 5. Adoption: what gets traction

Numbers read on 30/10/2026 from GitHub (all 955 repos in the HACS default dashboard list) and [analytics](https://analytics.home-assistant.io/). Reddit blocks automated reading, so Reddit claims below come from the authors' own posts on the forum.

### The base

| Signal | Value | What it means |
|---|---|---|
| HACS installed | 402,731 installs, **71%** of those reporting integrations | Before 2026.11. From 2026.11 the Marketplace is in 100% |
| Companion app (`mobile_app`) | 488,377, **86%** | Anything rendered by the frontend reaches phones |
| HA OS / Container | 79.6% / 17.7% | Apps reach ~80%; cards reach all |
| Own SSL certificate configured | 20,515 | Few users expose Home Assistant over HTTPS themselves; standalone remote access is a real barrier |

### Cards vs standalone

| Project | Kind | Stars | State |
|---|---|---|---|
| [Mushroom](https://github.com/piitaya/lovelace-mushroom) | Cards | 5,234 | ~4,900 release downloads/day |
| [Bubble Card](https://github.com/Clooos/Bubble-Card) | Cards | 4,680 | ~7,700/day; own subreddit and a 150-page forum thread |
| [Dwains Dashboard](https://github.com/dwainscheeren/dwains-lovelace-dashboard) | Generated dashboard in HA | 2,079 | Successor started 06/2026 |
| [ha-fusion](https://github.com/matt8707/ha-fusion) | Standalone (App + Docker) | 3,022 | Abandoned since 10/2024; the active fork kept 2.5% of the stars |
| TileBoard | Standalone | — | Repo gone |
| [GlassHome](https://community.home-assistant.io/t/glasshome-a-dashboard-with-70-cards-for-home-assistant/1021664) | Standalone, freemium | 34 | Forum launch 08/2026: 2 likes, replies mostly about the paywall |

Release downloads per day are a rough proxy (every install and update downloads the asset), not unique users.

Reading: **standalone dashboards aren't dead, but they're a niche that keeps losing maintainers, and users don't follow forks.** Cards and generated dashboards hold the installed base. Cards break too (2026.2 rewrote `ha-select`; 2026.3.1 broke card-mod CSS), mostly when they use internal elements.

### What made recent projects take off

Three visual projects of 2025–26 grew fast with no prior audience:

| Project | What | Stars | Time |
|---|---|---|---|
| [Helios](https://community.home-assistant.io/t/custom-card-helios-a-live-2-5d-energy-scene-for-your-home-assistant-energy-dashboard/1011416) | 2.5D energy scene, one card | 1,051 | 6 months (05/2026) |
| [HA-Animated-cards](https://github.com/Anashost/HA-Animated-cards) | Animated cards | 1,260 | 11 months |
| [easy-floorplan](https://github.com/nicosandller/easy-floorplan) | Floor plan card | 641 | 5 months |

The pattern is the same in all three:
- **A striking visual** that reads in a screenshot or a 10-second clip.
- **One card, one install**, as a custom repository first, with the HACS PR filed at the same time.
- **Launch on r/homeassistant**, then the forum's custom cards category. Helios reported "a few hundred active installs" two weeks after its Reddit post.
- **Runs on weak tablets** (Helios avoids WebGL on purpose and says so).

Other signals:
- Supply exploded: 599 of the 955 HACS dashboard plugins were created in 2025–26. Standing out takes a distinct idea, not one more card. Pulse's radial object is that.
- Regional YouTubers matter: simon42 (German) built his own dashboard strategy (277 stars) with an active forum. Germany is the biggest country in analytics (138k installs, US 121k).
- A screenshot alone can earn stars without lasting installs ([hass-config](https://github.com/matt8707/hass-config), 5.2k stars, unmaintained). Stars come from the look; installs come from being easy and kept up to date.
- Money: donations (Ko-fi, Patreon) and optional cloud extras are tolerated (Ultra Card's paid cloud integration: 468 installs). Paywalls inside the card are not.

### Where Home Assistant is going, and the overlap risk

Home Assistant is moving toward **auto-generated, area-based dashboards that surface problems**: the Home dashboard is the default (2026.2), and 2026.10 added security warnings (open doors and the like) on it. A plain "alerts by urgency" list is exactly what core is absorbing.

What core is unlikely to copy is Pulse's *interaction*: one object per system, urgency as depth, zoom to drill in. Two consequences:
- Pulse should **read Home Assistant's own signals** (areas, Home summaries, repairs, update entities, the new security warnings) instead of only its own rules, so it complements the default dashboard instead of competing with it.
- Core also opened the doors Pulse needs: "Community dashboards" in the new-dashboard dialog (2026.5) and community card suggestions in the card picker (2026.6), framed as an Open Home Foundation goal to "make building a dashboard feel as natural as building an automation".

## 6. Business implications

Updates `../coordinacion/pulse-venta-ha.md` (25/10) with what changed:

- **The free channel is now much stronger.** HACS needed a separate install and a GitHub account. The Marketplace is in every install from 2026.11, browsing needs no GitHub account, and listings show installs and stars. A free Pulse card is the best marketing Pulse can have.
- **License.** The catalog requires a GitHub-detected, OSI-approved licence that doesn't restrict use ([HACS include rules](https://www.hacs.xyz/docs/publish/include/); the new contributor page doesn't repeat it, assume it still holds). FSL doesn't qualify. The Marketplace build should be MIT.
- **Paid features can't be inside the Marketplace build** without community backlash ("paywall inside HACS") and the code is readable anyway. Where paid fits:
  - the standalone app and App (round screens, wall panels, kiosk niceties, multi-screen setups),
  - a "Pulse Pro" key for things that are maintenance, not components (alert rules library, ready-made systems per brand, compatibility with each Home Assistant release),
  - hardware bundles (Pi + round screen).
- **Review time.** `hacs/default` had 695 open non-draft PRs on 30/10/2026; the last merged batch waited one week to two months. Until listed, users can add the repo by link ("Add from link"). Plan the launch around that wait.
- **"Works with Home Assistant"** still doesn't apply to dashboards.

## 7. Recommended plan

**Step 1: split core and shell (small).**
- Define a `PulseSource` interface with what `main.ts` uses: `states`, `units`, `status`, `call`, `onChange`, `onStatus`. Two implementations: the current WebSocket client, and one over the `hass` object.
- Make the render mount on an element it's given (today Zumly mounts on the page's `#canvas` and the tune panel goes on the page).

**Step 2: `zumer-pulse` card + `zumer-pulse` dashboard strategy, one file (medium).**
- Card: plain custom element, Orbit and Zumly bundled, CSS adopted into the shadow root, Orbit's `@property` registered at document level. `getGridOptions` for sections; full height in a panel view. Visual editor with `getConfigForm` (which systems, which areas).
- Strategy: systems from areas, devices and domains; one panel view.
- Test on Home Assistant 2026.11 (update the local Docker), in the iOS and Android Companion apps, and on a tablet with kiosk-mode.

**Step 3: publish (small, slow).**
- Public repo, MIT, `hacs.json`, releases, README with images and a GIF. PR to `hacs/default` early, because of the review queue. Meanwhile, a My link for "Add from link".
- Launch post on the forum ("Share your Projects") and r/homeassistant with a video.

**Step 4: standalone stays, cleaned up (medium).**
- Replace the server-side password login with `home-assistant-js-websocket` `getAuth()` (OAuth, no server needed), `subscribe_entities` and registries.
- Package as Docker image and Home Assistant App (`ingress`, `panel_admin: false`, `base: './'`).
- Aim it at round screens and wall panels; this is where paid features go.

**Later:** section strategy (one-system Pulse), Pulse badge, ESPHome YAML export, custom view layout as an Orbit showcase.
